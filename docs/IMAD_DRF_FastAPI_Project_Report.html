IMAD Project Report · Backend Framework Study

Django REST Framework and FastAPI

System architecture, frontend and backend design, MVP workflow, feasibility, and technical research

This project implements one product-management API twice, using Django REST Framework (DRF) and FastAPI, and connects both implementations to the same React interface. The result is a hands-on comparison of request validation, persistence, documentation, testing, and local HTTP measurements under a deliberately small, repeatable workload.

Executive finding. The saved benchmark snapshot reports lower latency and higher observed throughput for FastAPI on all three tested routes in this particular local setup. The snapshot is not a universal framework ranking. Both implementations provide matching product rules and API status behavior for the covered contract tests, while retaining framework-specific validation wording and implementation structure.

1. Purpose and scope

The assignment asks for a practical comparison of two Python API frameworks. To make the comparison concrete, both services expose the same small product catalog and are exercised through one browser interface. A user can switch implementations while keeping the interaction model, product fields, HTTP methods, and expected status codes comparable.

The MVP focuses on the core learning outcomes: REST-style CRUD, request validation, a persistent local store, an external sample-data import, generated API documentation, cross-framework contract checks, and a reproducible benchmark. The current implementation is an educational prototype. It does not include authentication, multi-user ownership, payments, inventory workflows, cloud-managed infrastructure, or production observability.

Questions the prototype answers

  • How do DRF serializers and Pydantic schemas express the same product rules?
  • How do two frameworks produce equivalent endpoint behavior?
  • What does a small local benchmark actually measure?
  • How does frontend backend switching work when the data stores are independent?

Success criteria

  • Both APIs run independently and expose the same versioned product routes.
  • The same valid request produces the same meaningful result in both services.
  • Invalid inputs and missing IDs produce predictable error status codes.
  • Tests isolate local data and mock the external product source.
  • Performance claims come from recorded measurements, not constants in the interface.

2. System architecture

The React application is a client of two independent API processes. Each API owns its own SQLite file. The backend selector changes the API base URL used by the frontend, so switching frameworks changes which local product catalog is displayed. DummyJSON is contacted only when a user explicitly imports products; it is not a live data proxy.

Why separate SQLite files? Separate files preserve each service’s independent state. This makes the comparison visible and avoids silently sharing one persistence implementation between frameworks. A product created or imported into FastAPI does not automatically appear in DRF. The trade-off is that demos need to create/import data in both catalogs to compare identical workflows.

4. Frontend design and workflow

The frontend is implemented in frontend/src/App.jsx and styled in frontend/src/style.css. A single React page keeps the demo easy to follow. The current backend selection is held in React state. The page’s data-framework attribute also controls the visual theme: FastAPI uses the light presentation and Django REST switches to the dark presentation, making the selected implementation visually explicit.

Interface areas

  • Product catalog: loads the active service’s list, displays health, filters by search text, provides create/edit/delete controls, and refreshes from that service after writes.
  • Backend switcher: selects FastAPI on port 8000 or DRF on port 8001; a selection triggers the active list and health request. It does not merge the two databases.
  • DummyJSON import: submits a POST request to the selected backend, then displays fetched, created, skipped, and cache status.
  • Implementation and benchmark cards: shows short code examples and loads saved benchmark/quality JSON from the frontend’s public report directory.
  • API Testing Lab: sends named validation and PATCH scenarios to both services, then displays expected and actual statuses, client-side latency, and expandable JSON responses.
  • Research and docs: explains the actual synchronous implementation and links to each backend’s interactive API docs.

React components and local state keep the interface reactive; event handlers call the selected API and update the visible result. Vite provides the development server and production build pipeline. React’s documentation describes the component/state model; Vite documents its development server and static production build. React Quick Start · Vite Guide.

5. Backend implementations

FastAPI service

The FastAPI application is concentrated in backend/fastapi_app/main.py. It initializes a SQLite table on application lifespan startup and inserts three starter products only when the table is empty. Routes are synchronous def path operations. SQLite access uses Python’s sqlite3; DummyJSON is fetched with synchronous httpx.get. FastAPI creates the OpenAPI schema from route and Pydantic type declarations, and serves Swagger UI at /docs and ReDoc at /redoc.

ProductInput defines create/replace fields and rejects unexpected keys through Pydantic’s extra="forbid". ProductPatch makes fields optional for partial updates, rejects null when a field is explicitly supplied, rejects empty patches, and returns only supplied fields through model_dump(exclude_unset=True). This avoids applying omitted fields as null/defaults.

Django REST Framework service

The DRF service is organized as a Django project under backend/drf_app/. The Product Django model defines storage; migrations create the schema and a starter dataset. ProductSerializer maps and validates API values. ProductListView and ProductDetailView implement collection and item routes using regular synchronous APIView handlers and Django ORM methods. drf-spectacular serves OpenAPI at /api/schema/ and Swagger UI at /api/schema/swagger-ui/.

A project exception handler normalizes DRF validation errors into the shared {"detail":[{"loc":...,"msg":...,"type":...}]} shape and maps validation to HTTP 422. Framework-specific text and some error locations may still differ, which the report and UI acknowledge.

Why implement both instead of wrapping one?

The point of the MVP is to compare actual framework mechanics. FastAPI uses Pydantic request schemas and direct SQLite code in one application module. DRF uses Django model/serializer/view layers. Both independently implement persistence and validation so the comparison includes framework structure, not just two URLs forwarding to a common engine.

6. API contract and validation rules

Both APIs are versioned under /api/v1. Successful response bodies use a common data wrapper; lists also provide a meta object. The custom DRF exception handler and Pydantic validation output use a common detail array and HTTP 422 for field validation errors. Not-found behavior is HTTP 404.

PUT is a full replacement; PATCH is a partial update. The test contract ensures a valid PATCH updates only the supplied field and preserves the remaining product fields. This explicit distinction prevents a partial request from accidentally erasing data. Exact validation wording remains implementation-specific even when status, envelope shape and rules align.

7. DummyJSON import workflow

Each import endpoint requests up to 30 products from DummyJSON with only the fields used by the local product model: title, description, price, category, stock and thumbnail. The upstream ID is not used as a local primary key. The API validates the full response before writing records and maps upstream data into the local schema. Duplicate detection uses the local title/category pair, protected by the DRF model/query logic and a FastAPI SQLite uniqueness constraint.

A successful first import reports fetched source rows, the number newly created, and skipped/existing rows that match prior local records. Repeated imports are designed to create no duplicates. Both applications maintain a process-local five-minute cache; separate processes have separate caches. The HTTP calls are synchronous, and tests replace the HTTP responses with mocks so test results do not depend on the public service. DummyJSON documents that its add/update/delete endpoints simulate writes rather than persisting them, which is why this project stores imported products locally. 8. MVP process and feasibility

Implementation sequence

  1. Define a shared contract. Agree the product fields, validation limits, routes, response wrapper and status expectations before comparing frameworks.
  2. Build the FastAPI version. Add typed create/patch schemas, routes, SQLite initialization, health and import behavior.
  3. Build the DRF version. Add a Django Product model, migrations, serializers, APIViews, exception normalization and matching import behavior.
  4. Connect a single React UI. Use environment-configurable base URLs and a selector rather than duplicating the page for each framework.
  5. Verify equivalence. Use isolated test databases, mocked upstream responses and contract tests across both services.
  6. Measure and explain. Run the local benchmark, count source lines with declared boundaries, and document limitations and research findings.

Technical feasibility

The prototype is feasible for a small academic team: the data model is compact, both frameworks have mature request-validation and SQLite support, and the browser talks to ordinary JSON endpoints. The local setup needs Python, Node, and three processes; Docker Compose can simplify that presentation setup.

Academic feasibility

The project is bounded enough for a third-year BTech ICA: one resource, one external import, two implementations, tests and a limited benchmark. The code exposes the concepts being studied instead of hiding them behind a large platform.

Feasibility conditions and dependencies

  • Install compatible Python dependencies separately for the FastAPI and Django apps, then install frontend packages using the lockfile.
  • Keep ports 5173, 8000 and 8001 available, or configure the Vite environment values to use alternate API addresses.
  • DummyJSON import needs outbound network access; CRUD, tests and benchmark do not.
  • Local SQLite is appropriate for a small demo and repeatable tests. Concurrent production workloads need a production database and deployment review.
  • Team work allocation: dev and Nimitt are assigned backend work; Parth and Krupa are assigned frontend work.

9. Tests and quality evidence

The project contains FastAPI tests, Django REST tests and cross-framework contract tests. The combined contract fixture uses temporary SQLite files and Django migrations in an isolated test database. HTTPX upstream responses are mocked for import tests, including malformed data and timeout handling. This arrangement keeps tests deterministic and avoids using DummyJSON availability as a test dependency.

The cross-framework coverage includes create/list/retrieve/health behavior; price boundary failures; missing required fields; unknown fields; wrong types; negative stock; malformed image URLs; PATCH partial preservation, invalid/empty/null inputs and missing products; and import counts, repeat behavior, empty response, malformed upstream response, invalid product and timeout. 12. Technical research

12.1 Synchronous and asynchronous execution

A synchronous function runs step by step and does not yield control while waiting for a blocking operation. An asynchronous coroutine can suspend at await while waiting on a compatible nonblocking operation, allowing the event loop to schedule other work. This primarily improves concurrency for workloads with substantial I/O waiting; it does not automatically accelerate CPU-bound work. Concurrency and parallelism are different: asynchronous scheduling overlaps waiting tasks, while parallel execution performs work simultaneously on multiple cores/processors.

FastAPI supports both def and async def route handlers. Its official guidance says regular def path operations are run in an external threadpool so blocking calls do not directly block the event loop. This project uses regular synchronous route functions and synchronous SQLite/HTTPX operations. Therefore, this project does not demonstrate async-native database or HTTP behavior. The FastAPI runtime can still use its normal threadpool path for sync handlers, but the business logic itself is not written as an awaitable flow. See the FastAPI concurrency guidance.

Django can run async views under ASGI and provides async APIs for parts of its ORM and other subsystems, while sync/async adapters may be needed for other libraries. This application uses standard synchronous DRF APIView methods and ORM operations, so it is likewise a synchronous comparison. A future async experiment should be isolated and controlled: same database, endpoint, server concurrency, warm-up, requests, and trial count, with async-capable I/O dependencies throughout the request path. See Django async support.

12.2 Serializers and Pydantic

DRF serializers translate complex Python/model values to primitive API representations and validate incoming data before saving. In this project, ProductSerializer defines model-facing fields, strict string/number/integer behavior, constraints and URL checks. DRF’s partial=True mode lets the same serializer accept a PATCH containing only a subset of fields; the custom serializer rejects an empty partial request. Serializer validation errors are normalized by a project-level exception handler.

Pydantic models use Python annotations plus field constraints and validators to parse and validate incoming data. FastAPI binds a Pydantic model to the request body and includes its schema in the generated OpenAPI contract. The project uses a create/replace schema and a separate partial-update schema so omitted PATCH fields are distinguishable from explicit values. Pydantic is configured to forbid extra keys. Pydantic validation can coerce certain values unless strictness/custom rules are selected; this code adds checks for booleans masquerading as numbers and fractional stock, then enforces project-specific field limits. See the official DRF serializer guide, FastAPI request-body guide, and Pydantic model documentation.

12.3 When to choose each framework

Choose DRF when the application already uses Django or benefits from Django’s ORM, admin, authentication/authorization components, middleware and established conventions. DRF serializers and generic views fit a model-centric API and a team familiar with Django’s project structure. The trade-off is accepting the Django ecosystem and its broader application model when only a small API surface is needed.

Choose FastAPI when an API-first service benefits from type-annotated request/response schemas, concise route definitions and OpenAPI documentation generated from those definitions. FastAPI is also a sound choice for I/O-heavy async endpoints when dependencies support async and the full request path is designed accordingly. It does not require every endpoint to be async; sync functions are supported and dispatched through a threadpool.

Decide using requirements, not slogans. Evaluate the existing stack, integrations, team skill, administration needs, data model, request mix, operational constraints and representative tests. The benchmark here can prompt discussion but cannot substitute for workload-specific measurement.

12.4 API documentation, caching and data ownership

FastAPI produces OpenAPI from route signatures and Pydantic models, with interactive docs at /docs and /redoc. The Django service uses drf-spectacular to generate a schema and Swagger UI. Generated documentation should be treated as part of the API contract and checked against actual status/error behavior.

The in-memory source cache reduces repeat upstream requests during the five-minute TTL, but it is per process and lost at restart. It is not a shared production cache. The local SQLite products are persistent independently of that cache. The data source is illustrative; DummyJSON add/update/delete operations are simulated and not durable, so the prototype imports its sample data into its own SQLite stores.

13. Benefits, risks, and conclusion

Benefits

  • Concrete comparison: both frameworks solve the same domain task and speak the same API contract.
  • Visible persistence behavior: separate SQLite databases make backend ownership and switching tangible.
  • Validation learning: the lab demonstrates required fields, numerical boundaries, strict types, unknown keys, URL checks, PATCH and missing IDs.
  • Reproducible experimentation: local tests isolate data and mock upstream traffic; the benchmark records its configuration and samples.
  • Low startup cost: SQLite and local development servers keep the setup attainable for a classroom demonstration.

Risks and limitations

  • Two backends mean duplicate implementation and maintenance work; the dual architecture exists for comparison, not because a single application should normally duplicate its API this way.
  • SQLite is suited to this prototype’s small data, not a conclusion about production storage, write contention or scaling.
  • Benchmark numbers are sensitive to software versions, machine load, worker settings and the tiny fixture size. The measured run has only 90 samples per route.
  • Process-local import caches are not shared among workers or machines.
  • External import depends on network access and upstream response shape, though failures are handled and tests use mocks.
  • The project does not provide authentication, authorization, production secrets management, TLS termination, monitoring, backups or managed database operations.
  • API Testing Lab scenarios create temporary test products against live local APIs; the presenter should use a demonstration catalog and verify cleanup.

Conclusion

The MVP is feasible and demonstrates how framework choices affect validation style, application structure, documentation and local request performance. The saved benchmark favors FastAPI on its measured test conditions, and the saved code-size buckets are close rather than indicating a large DRF verbosity penalty. Both approaches meet the project’s tested product contract. The meaningful trade-offs are ecosystem fit, development conventions, validation workflow, async requirements and team experience. No universal winner follows from this small prototype.

Viva questions and concise answers

QuestionAnswer to prepare
Why separate SQLite databases?To keep backend persistence independent and make the selected API’s catalog explicit; each service owns its IDs and records.
What is the difference between PUT and PATCH?PUT replaces the full resource representation; PATCH changes supplied fields. This project’s empty PATCH is rejected and omitted fields remain unchanged.
How does DRF validate input?Serializer fields parse and validate request data; is_valid() runs before save and validation errors are formatted by the project exception handler.

Can we conclude FastAPI is faster?Only for the exact saved local run. The sample size, tiny dataset and one-worker configuration are not a universal or production benchmark.
Which framework would you select?DRF for Django ecosystem/model/admin fit; FastAPI for typed API-first services and async-capable I/O when dependencies support it. Choose based on actual requirements.
